# Исследование серии CayleyPy и план проверки качества

Дата проверки: 10 сентября 2026. Прочитаны публичные страницы Overview/Description/Evaluation в авторизованном браузере. Это исследование требований; итоговым материалам ещё не присвоены оценки.

Число слов ниже — ориентир по видимому тексту main страницы, включая элементы интерфейса и математические примеры. Это НЕ точный объём авторского описания. При финальной редактуре считать отдельно чистый текст разделов и сравнивать длину соответствующих разделов.

| [SuperCube from IHES](https://www.kaggle.com/competitions/cayleypy-ihes-cube) | 1965 | Источник 1003 задач/слов и ровно 18 ходов; отличие — ориентация картинок центров, 72 вместо 54 позиций |

Во всех 11 просмотренных страницах присутствуют математический/Cayley-graph контекст, связь с reinforcement learning, представление задачи как сортировки, суммарная длина пути, dot-separated submission и Custom Metric. Это выявленная структура семейства, а не основание копировать текст дословно.

Замеченные ошибки образцов важны для качества: IHES описывает 1003 входа, но в одном месте говорит о сумме по 1000; ссылка sample ведёт к другому соревнованию. Christopher’s Jewel содержит несовместимые размеры в разных абзацах. Новое соревнование должно сохранять стиль, но исправлять такие расхождения собственными проверенными числами.

## Структура новых английских страниц

1. **Overview / Description:** краткая цель; ordinary 333 versus IHES; 54 метки; 18 поворотов; информатический и математический взгляд; RL/pathfinding; ссылки на серию, статью и baseline.
2. **Evaluation:** Brief → точные состояния/операции → сумма длин → формат Submission File → пример пустого пути → ошибки и корректность.
3. **Data:** таблица каждого public-файла, типов колонок, описания JSON, гарантии обратных слов, повторяемость, происхождение и лицензия.
4. **Rules:** стандартная структура community competition; допустимые внешние вычисления/совместная работа/публикация кода; один согласованный scoring protocol; host benchmark не претендует на призовое место. Юридические условия не придумывать от имени Kaggle.
5. **Timeline / Prizes / FAQ:** фактические даты, UTC и местное время, Kudos, что значит средний слой/пустой путь/невалидный путь, как проверить сабмит.
6. **Visuals:** собственная схема 54 номеров и слоёв, обложка; не перерисовывать центры IHES как ориентированные в обычном 333.

Рабочий объём Description+Evaluation+математического контекста — около 2200–2800 английских слов без меню/числовых массивов. Это редакторский ориентир относительно серии, не способ получить искусственные 90%. Не заполнять объём повторами.

## Рубрика требуемого соответствия ≥90%

Проверять каждую пару «наш материал / одно из 11 соревнований». Один итоговый средний процент не заменяет проверку каждого свойства. Матрица: `reference,dimension,check_id,applicable,pass,evidence,reviewer_note`.

| Измерение | Проверяемые признаки | Условие |
|---|---|---|
| Идея | Минимизация пути; все данные/операции доступны; исследовательский benchmark; сопоставимость методов; отсутствие подмены задачи | ≥90% применимых пунктов; смысл задачи обязателен |
| Структура | Вводная, описание головоломки, матконтекст, данные, метрика, пример CSV, связанные задачи, источники, стартовый код, FAQ | ≥9 из 10 + объяснение неприменимых пунктов |
| Полнота | Все файлы/поля/ходы/цель/ID/пустота/ошибки/score/даты/лицензия описаны | Технические поля 100%, редакторские ≥90% |
| Подача | Английский научный тон, понятные заголовки, примеры, формулы, ссылки, умеренный объём разделов, отсутствие рекламных/ложных заявлений | ≥90% по явным редакторским проверкам |
| Форма артефактов | JSON перестановок, test, sample, metric, baseline, документация, воспроизводимость и публикационные ссылки | 100% обязательных файлов; ≥90% применимой формы |
| Техническая корректность | 18 правильных ходов, mapping, все replay, пустой путь, invalid rejection, итоговая сумма, sandbox, неизменность данных | **100%, ни один провал не усреднять** |

Для каждого процента хранить числитель/знаменатель и ссылку на конкретный материал. `Not checked` не равно Pass; `Not applicable` требуется обосновать. Пока артефактов нет, значения **Pending**, а не 90 или 100. Степень сходства стиля — редакторская оценка, не статистический факт.

## Официальный путь создания Kaggle

- [Hosting a competition from CLI](https://github.com/Kaggle/kaggle-cli/blob/main/docs/competition_creation.md): authenticated create unlaunched → pages → public data → private solution → settings → launch. У документации API-минимум kagglesdk 0.1.31; фактический установленный CLI проверить командой help/version перед использованием.
- [Setup guide](https://www.kaggle.com/docs/competitions-setup), прочитан в браузере: Host → Evaluation Metric; Python custom metric с аннотациями; без интернета, лимит 30 минут; sandbox до запуска; успешный сабмит можно отметить Benchmark.
- [Submit CLI](https://github.com/Kaggle/kaggle-cli/blob/main/docs/competitions.md): `--sandbox` предназначен для host/admin; сохранить submission ref и статус scoring. Не путать успех загрузки с успешной оценкой.
- [Kaggle Terms](https://www.kaggle.com/terms): участие организатора не должно влиять на определение победителя; используем host sandbox/Benchmark, а не создаём второй аккаунт участника.

Отдельно в реализации: открыть Data/Rules источника IHES и ближайших кубических соревнований, подтвердить лицензию повторного использования и действующие team/submission limits. Обзор 11 страниц уже выполнен; юридические/host-настройки всех 11 не объявляются исследованными.

## Публикация без повторных ручных кликов

Реализовать `publish_competition.py` с этапами и receipt. Он читает утверждённые файлы, вызывает официальный CLI и сохраняет ID, hashes, время, результат. Никогда не читает cookies браузера. Секрет — из штатного локального Kaggle API/secret store, не из публичного notebook/output.

`create` создаёт лишь один черновик; при ошибке/таймауте сначала искать уже созданный объект по slug/receipt. `pages` обновлять по имени. `data update` заменяет весь опубликованный набор: передавать полный whitelist public-файлов, а не одиночный изменённый файл. `solution` загружать отдельно и дождаться Ready.

Custom metric registration/выбор через Host UI, если действующая CLI/SDK не дают документированного способа. Не считать эту операцию автоматизированной заранее. Проверить настройку lower-is-better, 0 десятичных знаков, правильный deadline, public leaderboard и наличие sample.

Для ноутбуков использовать существующий `work/kaggle_publish_cua.js`: Save Version → Save & Run All, проверить Version History и точную scriptVersionId; это не интерактивные локальные тесты. После успешных sandbox и QA — Launch, затем повторно открыть публичный URL и фактический deadline.
